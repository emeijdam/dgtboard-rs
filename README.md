# dgtboard

Read a [DGT](https://www.digitalgametechnology.com/) electronic chess board over
USB / serial, in Rust — board state, FEN, and move detection. Runs natively
**and in the browser** via WebAssembly + the Web Serial API.

DGT serial e-boards — including the USB models, which expose an FTDI virtual
serial port — speak a small byte protocol at **9600 baud, 8N1**.

## Workspace layout

The protocol logic is split from the I/O so the same code runs on a serial port
or in a browser:

| Crate / dir       | What it is                                                            |
| ----------------- | --------------------------------------------------------------------- |
| **`core/`** `dgtboard-core` | Pure protocol: byte framing (`Decoder`), board/FEN, move detection, and (optional `rules` feature) rules-aware refereeing via `shakmaty`. No required deps, no I/O — compiles to wasm. |
| **`native/`** `dgtboard`    | Serial transport (`DgtBoard`), the `dgt` CLI, and the connection `doctor`. Re-exports the core. |
| **`wasm/`** `dgtboard-wasm` | `wasm-bindgen` bindings over the core. |
| **`web/`**        | A zero-install browser demo: live board over Web Serial. |
| **`viz/`** `dgtboard-bevy`  | A 3D WebGL/native viewer (Bevy 0.14): a photoscanned marble set (CC0), PBR lighting, shadows, bloom, orbit camera — driven by the core `Decoder`. |
| **`web3d/`**      | The 3D viewer as a zero-install Web Serial page. |

```
serial port / Web Serial  ──bytes──▶  Decoder ──Event──▶  MoveTracker ──▶  FEN / moves
                                       └──────────── dgtboard-core ───────────┘
```

## Browser demo (WASM + Web Serial)

Read your physical board live in a Chromium browser — no app, no server, ~0.7 MB
of wasm (it bundles a full chess-rules engine). The page **referees** the game:
illegal moves are flagged, the king in check is highlighted, and checkmate /
stalemate are bannered.

```sh
./web/build.sh                 # builds web/pkg via wasm-pack
cd web && python3 -m http.server 8000
# open http://localhost:8000 in Chrome/Edge, click "Connect board"
```

Web Serial is Chromium-only (Chrome / Edge / Opera). The board still needs its
USB serial driver installed and approved at the OS level — run `dgt doctor` if a
port doesn't show up. (`web/pkg/` is generated by `web/build.sh`.)

## 3D viewer (Bevy + WebGL2)

`viz/` (`dgtboard-bevy`) renders the same live board as a real-time 3D scene:
Poly Haven's **photoscanned marble chess set** (["Chess Set" by Riley
Queen](https://polyhaven.com/a/chess_set), CC0 — `viz/assets/chess_set/`, 2K
textures), glossy PBR materials, a shadow-casting key light with coloured accent
lights, an HDR camera with bloom, and a manual orbit camera (left-drag to rotate,
scroll to zoom). The whole scene is driven by `dgtboard-core` — a system diffs
the decoded `Board` against the spawned pieces each frame. The glTF loads
asynchronously; until it's in (or if the assets are missing) a procedural
lathe set and flat tiles stand in.

It runs both natively (macOS Metal / Linux Vulkan) and in the browser on WebGL2,
from one feature set:

```sh
# Native — opens a window seeded with the start position to orbit and admire:
cargo run -p dgtboard-bevy --bin dgt3d

# Browser — build the wasm, then serve over http (Web Serial needs a secure
# context; localhost counts):
./web3d/build.sh
cd web3d && python3 -m http.server 8000
# open http://localhost:8000 in Chrome/Edge, click "Connect board"
```

Same transport split as the 2D demo: the JS opens the Web Serial port and pushes
received bytes into the wasm (`push_bytes`); Bevy drains them through the core
`Decoder`. The scene boots on page load (start position), so you can admire it
before connecting. The Bevy wasm bundle is large (multi-MB) and its first
compile is slow — both expected. `web3d/pkg/` and the `web3d/assets` symlink
(→ `viz/assets`, where the piece set lives) are generated by `web3d/build.sh`.

## Library

```rust
use dgtboard::{DgtBoard, Event};
use std::time::Duration;

let mut board = DgtBoard::open("/dev/cu.usbserial-XXXX")?;

// One-shot snapshot:
let pos = board.snapshot(Duration::from_secs(2))?;
println!("{}", pos);                 // ASCII board
println!("{}", pos.fen_placement()); // e.g. rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR

// Or stream live changes:
board.reset()?;
board.request_board()?; // seed full position
board.start_updates()?; // then per-square updates
loop {
    if let Some(Event::FieldUpdate { square, piece }) = board.poll()? {
        println!("{square}: {piece:?}");
    }
}
```

### Move detection

`MoveTracker` reconstructs whole chess moves from the per-square update stream,
emitting one `DetectedMove` once the board settles into a position exactly one
move ahead:

```rust
use dgtboard::{DgtBoard, Event, MoveTracker};
use std::time::Duration;

let mut board = DgtBoard::open("/dev/cu.usbserial-XXXX")?;
let start = board.snapshot(Duration::from_secs(2))?;
let mut tracker = MoveTracker::new(start); // White-to-move if it's the start position
board.start_updates()?;
loop {
    if let Some(Event::FieldUpdate { .. }) = board.poll()? {
        if let Some(mv) = tracker.update(board.board()) {
            println!("{}  {}", mv.uci(), mv.describe()); // e.g. "e2e4  ♙ e2-e4"
        }
    }
}
```

It classifies quiet moves, captures, en passant, castling, and promotion (the
hardware identifies the promoted piece). Intermediate states — a piece lifted,
a half-finished castle — are deferred until the move completes, and putting a
piece back without moving it produces nothing.

This is a geometric reconstruction, not a chess engine: it assumes the moves
played are legal and works out *which* move happened. It doesn't validate
legality, detect check/mate, or emit SAN. Two known edge cases: it can't know
whose turn it is if you start mid-game (it infers side-to-move from the first
move's colour), and castling is recognised most reliably when the **king moves
first** (the usual touch-move order).

The board only knows piece placement, so `fen_placement()` returns just the
first FEN field (no side-to-move / castling / counters).

### Rules & refereeing

The `rules` feature (on in the CLI and web demo) adds `RefereedGame`, which
validates each detected move against the real laws of chess using
[`shakmaty`](https://crates.io/crates/shakmaty) — so it catches **illegal
moves** and reports **check / checkmate / stalemate / draw** with SAN like
`Qh4#`:

```rust
use dgtboard::{DgtBoard, Event, RefereedGame, Ruling};
use std::time::Duration;

let mut board = DgtBoard::open("/dev/cu.usbserial-XXXX")?;
board.snapshot(Duration::from_secs(2))?;   // referee expects the start position
let mut game = RefereedGame::new();
board.start_updates()?;
loop {
    if let Some(Event::FieldUpdate { .. }) = board.poll()? {
        match game.update(board.board()) {
            Some(Ruling::Legal { san, status, .. }) => println!("{san}  {status:?}"),
            Some(Ruling::Illegal { uci })           => println!("illegal: {uci}"),
            Some(Ruling::BackInSync)                => println!("back in sync"),
            None => {}
        }
    }
}
```

When an illegal move is played the board is marked *out of sync*; it re-syncs
(`Ruling::BackInSync`) once you restore a legal position. `RefereedGame` also
exposes `checked_square()` for highlighting the king in check. The `dgt referee`
command and the browser demo are both thin wrappers over this.

## First time connecting? Run the doctor

DGT boards use an FTDI USB-serial chip with DGT's **custom** USB vendor id, so
macOS's built-in FTDI support doesn't bind to it. You have to install the FTDI
VCP driver and then *approve* it in System Settings — two easily-missed steps.
`dgt doctor` checks the whole chain and tells you exactly where you're stuck:

```sh
cargo run --bin dgt -- doctor
cargo run --bin dgt -- doctor --open-settings   # also jump to the driver-approval screen
```

```
[1/4] USB device   ✓  Board detected: DGT e-Board (VID 045b PID 8111)
[2/4] Serial port  ✓  /dev/cu.usbmodem01
[3/4] Driver       ✓  com.ftdi.vcp.dext [activated enabled]
[4/4] Security     ✓  Driver approved.
--------------------------------------------------
✓ Ready. The board is connected. Try:  dgt snapshot
```

If a step fails it points you at the fix: a data-capable cable, the FTDI VCP
driver download (<https://ftdichip.com/drivers/vcp-drivers/>), or the macOS
driver-approval screen (System Settings → General → Login Items & Extensions →
Driver Extensions on macOS 15+, or Privacy & Security on macOS 13–14). After
approving a driver, unplug and replug the board.

## CLI

```sh
cargo run --bin dgt -- doctor                   # diagnose connection / driver / security
cargo run --bin dgt -- list                     # show serial ports
cargo run --bin dgt -- snapshot                 # read the position once
cargo run --bin dgt -- snapshot --port /dev/cu.usbserial-XXXX
cargo run --bin dgt -- watch                    # live: print raw per-square changes
cargo run --bin dgt -- moves                    # live: print detected chess moves (UCI + description)
cargo run --bin dgt -- referee                  # live: validate moves, flag illegal, announce check / mate
```

`snapshot` and `watch` auto-select the port when exactly one USB serial device
is present; otherwise pass `--port` (use `list` to find it).

## Lichess puzzles

`dgt puzzle` fetches Lichess puzzles and referees them on the board. You set
up the position, play your move, and — since a DGT e-board has no lights —
the opponent's reply is printed in the terminal for you to execute; the tool
recognises it as the expected move, not a new one. Lichess's acceptance rule
applies: the solution move, or any move that checkmates.

```sh
cargo run --bin dgt -- puzzle                        # random puzzles, one after another
cargo run --bin dgt -- puzzle --daily                # today's daily puzzle first
cargo run --bin dgt -- puzzle --id m5n0s             # one specific puzzle first
cargo run --bin dgt -- puzzle --theme mateIn2 --difficulty harder --color white
cargo run --bin dgt -- puzzle --daily --keyboard     # no board: type moves in UCI
```

The screen shows the puzzle header (rating, themes, source game and players,
the last move played), the position as ASCII + FEN, and a live list of the
squares still to fix until the board matches. Then `✓ Kxh2` for a correct
move, `✗ Kh1 isn't it (expected Kxh2) — put it back` for a wrong one (the
puzzle counts a mistake and waits for the position to be restored), and
`← Black plays Ng4+ — play it on the board …` for the reply. At the end:
`Solved (3/3 moves, 0 mistakes)`; Enter continues with the next puzzle, `q` quits.

- `--keyboard` runs the whole flow without hardware: type moves as UCI
  (`e2e4`, `e1g1` or `e1h1` for castling, `e7e8q` for promotion); the move is
  turned into the lift/place updates a real board would send. `setup` jumps
  the simulated board back to the expected position; `fen <placement>` sets
  any position.
- A Lichess API token is optional. With one (`LICHESS_TOKEN` in the
  environment, or `--token-file <path>`), Lichess serves puzzles you haven't
  seen yet. It is only ever sent as the `Authorization` header — never
  printed; keep the file out of git.
- This is a trainer. Lichess has no API for submitting a puzzle solve, so
  nothing is sent back and your puzzle rating is unaffected. Time controls
  don't apply: take as long as you like.
- The client makes one request at a time and, on HTTP 429, waits a minute
  and retries once, as Lichess asks.

## Protocol notes

- Framing: byte 0 = message id with `0x80` set; bytes 1–2 are 7-bit length
  halves, `len = (b1 << 7) | b2`, length includes the 3-byte header.
- Square numbering: `0` = a8 .. `63` = h1 (row-major, rank 8 first) — already
  FEN order.
- Commands used: `SEND_RESET 0x40`, `SEND_BRD 0x42`, `SEND_UPDATE_BRD 0x44`,
  `SEND_VERSION 0x4d`. Messages handled: `BOARD_DUMP 0x06`,
  `FIELD_UPDATE 0x0e`, `VERSION 0x13`, `SERIALNR 0x11`, `BWTIME 0x0d`.
